## Findings (raised as MON-104+ engine/surface fixes — no number was adjusted)

1. **Split FY resolution between write and read path.** The capture write path uses the raw `?fy=` query value while the read path uses the config-normalised FY. An orphaned capture saves silently and then stays inert forever — the worst failure mode for a capture feature, because the user sees a successful save and no outcome. *Fix shape: one canonical FY resolver used by both paths; reject an unresolvable FY at the write boundary rather than persisting an unreachable row.*

2. **Div 152 capture gated behind `PSI_TYPES`.** The Div 152 card is rendered inside the same `isPsiRelevant` branch as the PSI card, so `PERSONAL_NAME` / `INDIVIDUAL` / `FIXED_TRUST` / `HYBRID_TRUST` / `TESTAMENTARY_TRUST` / `DECEASED_ESTATE` can **never** capture Div 152 facts — yet an individual selling an active business asset is the single most common Div 152 taxpayer. *Fix shape: Div 152 gets its own eligibility grammar, not PSI's.*

3. **No FY2026-27 tax year config.** The header reads "Financial Year 2026-27" while the bracket table and footnote read "FY25-26". The $18,201–$45,000 band is taxed at **16%**, not the legislated **15%** applying from 1 July 2026 — an **≈$268 overstatement** on Reza's live position, re-confirmed on this run. *Fix shape: FY2026-27 config entry + a loud stale-FY surfacing when the requested FY has no config + a CI guard that fails the build when the current FY is unconfigured. Number-changing → Reza's click before merge.*

4. **The 80% one-client threshold is an inline literal in two places** — `psiClassifier.ts:181` (`oneClientPercentage < 0.8`) and `PsiAssessmentCard.tsx:212` — config-traced in neither. The card's "90% of total — the 80% one-client test applies" hint fired live on this run, so the drift risk is real and user-visible. **Extended by this run:** `Div152AssessmentCard.tsx` re-hardcodes the same class of constants — `Number(months) >= 180` gates the 15-year hint (the engine's own `FIFTEEN_YEAR_MONTHS = 15 * 12`), and `$6,000,000` / `$2,000,000` / `$500,000` appear as literal display copy against the engine's `MNAV_THRESHOLD` / `TURNOVER_THRESHOLD` / `RETIREMENT_LIFETIME_CAP`. *Fix shape: export the engine constants and have the capture layer read them; add a NeoAudit detector for tax-threshold numerals appearing outside `lib/tax-engine`.*

5. **Wrong citation on the PSB branch (user-visible today).** `PsiAssessmentCard.tsx:253` hardcodes `ITAA 1997 Part 2-42 · s86-15` for **every** outcome, so the non-attribution ($0) branch cites the *attribution* provision. The engine's own `citations` array correctly carries **s87-60** for the ATO-determination branch (and s87-18 / s87-20 / s87-25 / s87-30 for the other PSB routes) — the card discards `citations` entirely. This is a Ring-1 source-lock violation at the surface: the card restates engine metadata instead of rendering it. *Fix shape: render `result.citations`; delete the literal.*

6. **Duplicated citation in the Div 152 outcome rows.** Confirmed at source: the engine's `steps[].concession` string already contains the citation (`'50% active asset reduction (s152-205)'`), and `Div152AssessmentCard.tsx` renders `{s.concession} ({s.citation})` — producing `50% active asset reduction (s152-205) (s152-205)`, `Retirement exemption (s152-305) (s152-305)`, `15-year exemption (s152-105) (s152-105)` live. Cosmetic in effect, but the same defect class as Finding 5. *Fix shape: the engine emits a clean `concession` label and the surface renders `citation` once — one producer per string.*

7. **NEW — the s86-15 attribution is entity-surface-only, and the card reconstructs a value the engine does not expose.** Two parts, one root: `Div152Result` has no `gainBeforeConcessions` field, so `Div152AssessmentCard` computes `steps[0].runningGain + steps[0].reduction` to display "Gain after CGT discount" — arithmetically correct on every branch checked, but it is a surface deriving an engine value, which is exactly what the Calc-SSOT wall forbids. Separately, a PSI attribution under s86-15 is legally attributed **to the individual**, yet it currently reaches only the entity view and never the household position — documented as the Phase 41e.6/41e.7 company-dispatch deferral, and raised here so the deferral is tracked with an explicit issue rather than silently absorbing a legislated attribution. *Fix shape: engine returns `gainBeforeConcessions`; a tracked issue for routing s86-15 attribution into the individual's assessable income when the company dispatch lands.*
