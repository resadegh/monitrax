## §6 Before reverting — the one check that could redirect this

`masterFinancialService` returns `calculatedAt` at read time **and** a new `paygWithholding`, so it is recomputing, not serving a wholly stale row. But VR-041 recorded a live instance of exactly this trap: *the budget card rendered new captions over old numbers because the documented auto-regeneration did not fire on visit.*

So the question Code should answer first — minutes, not a rebuild:

**Is `masterFinancialService`'s income block read from a persisted snapshot that the flip writes but does not recompute on read?** If yes, the wiring may be correct and the defect is in the regeneration path — a much smaller fix. If no, the consumer was never wired and the brief's §5 applies as written.

**Either answer leaves the current production state unacceptable**, because §4's contradiction is live on Reza's Home screen now.

## §7 Instrument error — mine, corrected, and the procedure changed

My first attempt at the rendered checks found `/dashboard/tax` showing **$0** on every field. I had it drafted as a production P0.

It was not one. **Signing into `/admin/login` swapped the browser's app session to the admin account** — Home rendered entity *"admin"*, 3 properties, $3.9M, zero accounts, zero loans. The zeros were an account with no income rows. **Withdrawn.**

The run above is the re-run, in Reza's own session, with identity asserted from net worth $3,401,782 / 6 properties / 5 loans / entity *"Reza"* $2,651,782 **before any figure was read**. The producer half never depended on it — the relay is scoped to `?userId=91b6d7ce…` regardless of who is signed in — but it was re-confirmed against the screens anyway rather than asked to be taken on trust.

**Standing rules adopted, at Reza's direction:**

1. **No number is ever validated through the admin portal's own user.** Admin credentials open the relay door; the data behind it is always `?userId=` scoped to the account under test.
2. **Identity is asserted from a known figure before any rendered number is read.** A run that cannot prove its account is void and is reported as void, never as numbers.
3. **Ring-3 verifies Reza's account completely** — every number, every surface — before anything is called verified. Not a sample.
4. **The two sessions never share a browser profile.** The admin login silently overwrites the user session.
5. **Later, more datasets.** Reza's account is the reference now; a second and third will catch the shapes his does not have — a fixed-rate loan, an account with no income, a cross-collateralised property. Fixture data or consented test accounts, never anything fabricated in production.
